======================

------------

machines:

The clients reached the local repeater through SSH reverse tunnels.

SSH reverse tunnels
-------------------

Because the repeater was local and the clients were remote, SSH reverse tunnels
were used.

Rule:

    -R remote_port:local_host:local_port

Meaning:

    a connection to remote 127.0.0.1:remote_port is forwarded to
    local_host:local_port on the local laptop side.

Client 1 tunnel:

    ssh -J pasarela@kr.ls.fi.upm.es \
      -o Compression=no \
      -o IPQoS=lowdelay \
      -R 7401:127.0.0.1:7401 \
      ubuntu22@REMOTE_1

Client 2 tunnel:

    ssh -J pasarela@kr.ls.fi.upm.es \
      -o Compression=no \
      -o IPQoS=lowdelay \
      -R 7402:127.0.0.1:7402 \
      ubuntu22@REMOTE_2

Then each remote client connected to 127.0.0.1, but that local address on the
remote machine was forwarded back to the local repeater.

Script/runtime settings
-----------------------

Common runtime environment:

    PYTHONUNBUFFERED=1
    PYTHONMALLOC=malloc
    sudo

Reason:

    PYTHONUNBUFFERED=1
        avoids stdout buffering surprises.

    PYTHONMALLOC=malloc
        uses system malloc instead of Python's pymalloc allocator.

    sudo
        allows CPU affinity / scheduling / socket-related options to work when
        the OS requires privileges.

Remote clients used:

    --cpu 1

because the remote Ubuntu machines exposed CPUs 0 and 1.

Group: delay_hist_client_1_8.csv and delay_hist_client_2_8.csv
--------------------------------------------------------------

Topology:

    three-machine topology
    local WSL repeater on the laptop
    remote client 1 through an SSH reverse tunnel
    remote client 2 through an SSH reverse tunnel

Sync:

    --clock-sync enabled
    --clock-sync-samples 256

Centering:

    --center-delay enabled

Meaning:

    delay_ns is the one-way delay after applying the PTP-style clock offset:

        delay_ns = (client_receive_time_ns + clock_offset_ns) - repeater_emit_time_ns

    delay_centered_ns is not the one-way delay. It is only the difference between
    each corrected delay and the median corrected delay of this run:

        delay_centered_ns = delay_ns - median(delay_ns)

    Therefore delay_centered_ns measures jitter around the run baseline.

Observed summary:

    client 1:
        clock_offset_ns = 1454594568
        clock_sync_path_delay_ns = 10775961
        delay_center_ns = 2328057
        raw delay p50/p95/p99 ~= 2.328 / 5.753 / 6.644 ms
        abs centered p50/p95/p99 ~= 0.705 / 3.425 / 4.316 ms

    client 2:
        clock_offset_ns = 1516879712
        clock_sync_path_delay_ns = 12236104
        delay_center_ns = 6072834
        raw delay p50/p95/p99 ~= 6.073 / 12.260 / 13.100 ms
        abs centered p50/p95/p99 ~= 2.757 / 6.187 / 7.027 ms

Important interpretation notes
------------------------------

1. PTP-style sync is done before the measured loop.

   It does not run during the send/receive counts. Therefore it does not directly
   slow down later sends.

2. PTP over SSH reverse tunnels can be biased.

   PTP assumes approximately symmetric path delay:

       master_to_slave_delay ~= slave_to_master_delay

   With SSH reverse tunnels and a jump host, this may be false.

   Offset error is:

       offset_error = (delay_backward - delay_forward) / 2

3. Negative raw delay after PTP correction means the offset estimate is biased.

   A message cannot physically arrive before it was emitted. If corrected
   delay_ns is largely negative, the offset estimate is not reliable for absolute
   one-way delay.

4. --center-delay does not fix clocks.

   It computes:

       delay_center_ns = median(delay_ns)
       delay_centered_ns = delay_ns - delay_center_ns

   It is useful for jitter analysis around a run baseline, not for absolute
   physical one-way latency.

   In other words:

       delay_ns
           what each send appears to take after clock-offset correction

       delay_centered_ns
           how different that send is from the median send in the same run

   So --center-delay is not "the delay of each send". It is a per-count
   difference from the run median.

5. Different remote clients can have different offsets.

   In the three-machine setup:

       offset_1 = local_repeater_clock - remote_client_1_clock
       offset_2 = local_repeater_clock - remote_client_2_clock

   Since remote_client_1 and remote_client_2 are different machines, the offsets
   do not need to match.


Best current use of these CSVs
------------------------------

For absolute one-way delay:

    These CSVs are not reliable unless the three machines are externally
    synchronized with chrony/PTP/NTP or the SSH tunnel is removed.

For jitter/shape analysis:

    Use delay_centered_ns from the --center-delay runs.

For raw clock-drift/range inspection:

    Use the no-sync runs 5, 6, and 7, but interpret them only as timestamp-series
    shape/range, not physical delay.
